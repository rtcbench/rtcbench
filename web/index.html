The problem with browser-based testing

The standard approach to end-to-end SFU evaluation uses ChromeDriver or similar browser automation to simulate real participants. It works — but it burns CPU at a rate that makes large-scale tests prohibitively expensive.

A single ChromeDriver instance handling one video session consumes a disproportionate share of a CPU core. Scaling to hundreds of concurrent sessions requires a rack of bare-metal machines, just for the client side.

How it works

call.zip replaces the browser with a minimal Go process that implements just enough of the WebRTC stack to look like a real participant to the SFU. No rendering, no JavaScript engine, no DOM — only signaling, ICE, DTLS, and RTP.

1

Configure a test

Describe the room topology, participant counts, roles, and SFU target in a single YAML file.

2

Thin senders publish VP9

Sender bots read pre-encoded IVF files and stream VP9 over WebRTC — no encoder running, no GPU required. The SFU sees a real media stream.

3

Thin receivers subscribe

Viewer bots complete the full ICE/DTLS/SRTP handshake and receive RTP, measuring per-packet arrival time, jitter, and VP9 frame statistics — without ever decoding video.

4

Collect metrics

Structured logs capture video quality samples, connection state transitions, and signaling latency. Pipe them to your analysis tool of choice.

Features

⚙

Plugin-based SFU support

Each SFU is a plugin. Add a new platform by implementing a three-method Go interface.

🔄

Native WebRTC via Pion

Full ICE, DTLS, and SRTP — no browser, no Electron, no Node. Pure Go.

📹

Realistic VP9 traffic

Pre-encoded IVF clips are paced at real frame timings, producing authentic bitrate and packetization patterns.

📄

YAML configuration

Room count, viewers per room, sender count, join spacing, retry policy — all in one file.

📊

Video quality metrics

Per-frame VP9 statistics, RTP sequence tracking, and jitter measurement built in.

🌍

Auto client IP detection

Determines the correct local IP for ICE by routing toward the server — no manual network config needed.

Quick start

Requires Go 1.24+. Clone, build, and point it at your SFU.

$ go install call.zip/cmd/call.zip@latest

Write a config file:

# config.yml
apiVersion: call.zip/v1
kind: VideoCallStressTest
metadata:
  name: stress-test-1
spec:
  plugin: janus          # or: jitsi
  conference:
    name: 1234           # Janus room ID
    viewers: 25
    totalRooms: 10
    cameras:
      perRoom: 5
      fileType: ivf
      videoCodec: vp9
      directory: ~/vp9_clips
    joinPolicy:
      concurrency: 10
      viewersAlwaysRetry: true
      joinStartSpacing: 2s
  network:
    serverIP: 10.0.0.1
  pluginConfig:
    janus:
      serverRoot: https://10.0.0.1/janus
      allowInsecureHttps: true
  logging:
    console: true
    directory: /var/log/call-zip

Run it:

$ call.zip config.yml

Senders will publish VP9 streams and viewers will subscribe. Watch for ICEConnectionState: connected in the logs to confirm media is flowing.

Supported platforms

Each SFU plugin handles signaling and negotiation for its platform. The WebRTC media path is shared.

Janus VideoRoom plugin over HTTP REST. Senders publish via offer/answer, viewers subscribe using the multi-stream subscriber API. Static ICE candidate on port 10000.
Jitsi XMPP/BOSH signaling with Jingle for SDP exchange, targeting Jitsi Videobridge (JVB). Full sender and viewer roles supported.

Research

call.zip is the subject of a workshop paper submitted to SigComm 2026.

Call.ZIP: Low-Cost Video Conference Testing at Scale
SigComm Workshop ’26 — under review
We present call.zip, a lightweight and extensible framework for stress-testing SFU-based video conferencing systems. By replacing browser-based bots with thin Go clients that speak WebRTC natively, call.zip reduces client-side CPU overhead by over an order of magnitude, enabling large-scale SFU evaluation on a single machine. The framework supports multiple SFU platforms through a plugin interface and produces realistic VP9 traffic from pre-encoded IVF clips.
