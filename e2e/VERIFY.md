# Screenshot Verification Prompt

You are verifying screenshots from a video conferencing e2e test. Each SFU plugin
(janus, jitsi, livekit) runs 2 senders and 2 viewers. A headless Chromium browser
joins the conference and takes screenshots at specific times after joining.

## What the screenshots show

- **Header bar**: colored banner at the top identifying the SFU (blue=janus, green=jitsi, orange=livekit).
- **Sender tiles**: show a VP9 test pattern video generated by ffmpeg's `testsrc2` filter.
  The pattern has:
  - Vertical color bars (red, green, yellow, blue, magenta, cyan) as the static background
  - Multiple diagonal lines in various colors that continuously sweep across the frame
  - A gray rectangle/crosshair that moves around the frame
  - Dotted/dashed line patterns near the right side
  When video is playing, the diagonal lines and gray element change position EVERY SECOND.
  When frozen, all elements stay in the exact same position across multiple screenshots.
- **Viewer/non-publisher tiles**: show a colored circle with 2-letter initials (e.g. "VI", "EV", "V0").
- **Labels**: each tile has a name label at the bottom (e.g. "sender-abc123...", "viewer-xyz789...").

## Checks to perform

For each SFU, analyze all screenshots in sequence:

### 1. Layout check (from the first screenshot showing video, usually 05s)
- How many tiles show the color bar test pattern video?
- Expected: at least 2 sender tiles with video.
  Jitsi may show extra tiles (browser viewer + call.zip viewers as placeholders) — OK.
  Janus/LiveKit show a 2x2 grid: 2 senders with video, 2 viewer placeholders.

### 2. Video liveness check (MOST IMPORTANT)
For EACH sender tile independently, track the position of:
- The diagonal colored lines (they sweep continuously across the frame)
- The gray rectangle/crosshair element

Compare these landmarks between every pair of consecutive screenshots.

**LIVE**: Lines and gray element are in clearly different positions.
**FROZEN**: Lines and gray element are in the same position for 2+ consecutive seconds.

#### Freeze classification
- **Transient freeze** (2-4 seconds, then recovers): May happen during IVF loop restarts
  or JVB forwarding adjustments. Mark as WARNING but not FAIL, as long as the sender
  recovers and shows live video in later screenshots.
- **Permanent freeze** (5+ seconds with no recovery, or video disappears entirely):
  Indicates a session death or critical bug. Mark as FAIL.

### 3. Header check
- Correct SFU name in the header? Correct color? (blue=janus, green=jitsi, orange=livekit)

## Output format

```
=== {SFU_NAME} ===
header: {color} "{text}" — {PASS/FAIL}
layout: {N} tiles with video, {K} placeholders — {PASS/FAIL}
sender_1 ({label}):
  movement: [list pairs with YES/NO for each consecutive pair]
  verdict: {LIVE / TRANSIENT_FREEZE at Xs (recovered at Ys) / PERMANENT_FREEZE at Xs}
  result: {PASS / WARNING / FAIL}
sender_2 ({label}):
  [same format]
overall: {PASS / WARNING / FAIL}
```

**PASS**: Both senders live throughout, or only transient freezes that recover.
**WARNING**: Transient freeze detected (2-4s) but recovered.
**FAIL**: Permanent freeze, missing senders, wrong layout, or wrong header.
